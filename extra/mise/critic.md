# Критическая оценка MISE 2

Оценка по трём осям, заданным явно: **дисциплина проектирования языков**
(Хоар, Вирт, «наименьшее удивление», ортогональность, «ошибки должны быть
невозможны»), **адекватность предметной области** (лёгкие rule-driven системы
в духе Wander для авторов IF) и **анализируемость/верифицируемость** (fuzzing,
model checking, abstract interpretation для тупиков и неразрешимости).

Всё, что ниже, проверено по коду (`extra/mise/miselib`, `core.mise`, `SPEC.md`,
`tests/`), а спорные утверждения — экспериментами (список в § 6).

---

## 1. Что действительно хорошо (без этого критика бессмысленна)

Перечисляю честно, потому что часть выводов ниже — следствия того, что язык
сделан аккуратно.

- **Один блочный синтаксис и правило `key = value` / `key =` + отступ.**
  Декларации и логика не разъезжаются на два языка; нет «режимов» и heredoc-ов.
- **Строгий водораздел «строка в кавычках» vs «голое имя — символ».** Это
  решение действительно убирает целый класс ошибок (`_"..."` в STEAD3,
  строковые ссылки на объекты) и позволяет парсеру строить AST без таблиц типов.
- **Настоящий EBNF-раздел в спецификации** (`SPEC.md`, § 5, ~250 строк) плюс
  `core.mise` — декларативное описание API движка. Это выше среднего уровня
  документации DSL.
- **Тестовая дисциплина.** 131 негативный тест с точными сообщениями и номерами
  строк, 30 игр с побайтовыми golden-файлами Lua, транскрипты, сравнимые с
  оригиналами на metaparser, контракт `-stop`. Для DSL это редкость и это
  главный источник доверия к языку.
- **Диагностика с подсказками** (`did you mean …`) для имён полей, событий,
  перечислений и фаз обработчиков.
- **`STATIC`-проверки домена, а не только типов:** запрет перезаписи метода
  класса скаляром (`_check_override`), требование `return` при объявленном
  результате, запрет строкового литерала в `ref`-поле.

Это сильная инженерия. Проблемы ниже — не «сделано плохо», а «выбрана стратегия,
которая упирается в потолок»; и этот потолок стоит назвать.

## 2. Дисциплина проектирования языка

### 2.1. Язык определён чекером, а не спецификацией

`SPEC.md` — 941 строка, `miselib` — 3700 строк. Спецификация уже почти размером
с реализацию, и это не совпадение: **большая часть правил языка живёт не в
EBNF, а в 56 `raise`-инструкциях `checker.py`.** Каждая из них — неочевидное
правило: «`pass` в потомке запрещён после `return`», «маркер `->` у обработчика
обязателен», «`impl T` требует объявленной цели», «класс должен быть объявлен
выше места использования» и т. д.

Виртовская дисциплина требует обратного: сначала маленькая грамматика и
формальные правила, потом (и только потом) проверки, каждая из которых ссылается
на пункт спецификации. Здесь же EBNF покрывает *синтаксис*, а *семантика
допустимости* — это набор эвристик в коде, эволюционировавший от сообщений об
ошибках (это видно по коду: диагностики писались под конкретные грабли реальных
игр, а не выводились из модели).

**Следствие:** язык нельзя проверить на соответствие спецификации. Нет способа
сказать «эта программа на MISE 2 корректна по спеке», кроме «её принял
`checker.py` этой версии». Для DSL, который обещает автору стабильность,
это главный риск: правила будут меняться вместе с диагностиками, а не наоборот.

Что было бы дисциплинированно: таблица «правило — пункт SPEC — тест», и
EBNF-конформанс-тест (парсер принимает ровно язык грамматики). Сейчас EBNF уже
расходится с реализацией в мелочах (см. § 2.5).

### 2.2. Ортогональность: слишком много способов сказать одно и то же

Виртовский критерий — «одна концепция — одна нотация». В MISE 2:

| Понятие | Способы записи |
|---|---|
| объект/комната/сцена | `obj`, `room`, `story`, плюс `class`+экземпляр, плюс `mixin` (синоним `class`) |
| логика «на игру» | `impl game` |
| логика «на игрока» | `impl pl` |
| событие | `events`/`type event`, `event X` (= `impl mp : X`), паттерн глагола |
| вставка сырого Lua | `lua`-блок, бэктик `` `expr` ``, `extern fn` шаблон, `extern global` |
| тело функции | многострочный блок, `= <токен>`, `= \`lua\``, `= "шаблон"` (extern) |
| вложенность | `obj` внутри `obj` (дети), `with`/`found_in` (ссылки), `@room` (локация) |

Каждая пара по отдельности объяснима («sugar для краткости»), но вместе они
дают автору выбор без причины выбирать. Хуже: у этих форм **разная семантика**
(§ 2.3), так что выбор перестаёт быть косметическим.

### 2.3. Наименьшее удивление: места, где форма записи меняет смысл

Это самая серьёзная группа дефектов — не стилистическая, а семантическая.

1. **Однострочная функция — это макрос, многострочная — функция.**
   `emitter.py:44-47` и `emitter.py:545-548`: тело-строка без `local`/`return`
   и без перевода строки **не эмитится**, а вызовы подставляются текстом
   (`_expand`). Проверено: `fn one_line(x: num) -> num = x` даёт `local a = (1)`,
   а `fn multi_line(x: num) -> num` + `return x` даёт `local b = fn_multi_line(1)`.
   То есть **добавление `\n` меняет семантику**: рекурсия, идентичность `&f`,
   номера строк в трейсбэке, кратность вычислений.

2. **Подстановка аргументов негигиенична и дублирует вычисления.**
   `_expand` (`emitter.py:552`) подставляет аргументы в текст шаблона через
   `re.sub(r"\b" + param + r"\b", arg_text, body)`. Проверено:
   `fn pick(o: tbl) -> any = \`(rawget(o, 1) or rawget(o, 2))\``
   при вызове `pick mk` даёт `rawget(fn_mk(), 1) or rawget(fn_mk(), 2)` —
   **`mk()` вызывается дважды**. То же у `$1`-шаблонов `extern`: если шаблон
   использует `$1` дважды, аргумент вычисляется дважды. Плюс `$1` внутри
   Lua-строки шаблона (`"..." .. "$1" .. "..."`) будет подменён, потому что
   подстановка текстовая. И пост-обработка `re.sub(r",\s*\)", ")", …)` — это
   уже штопка шва, а не языковая конструкция.
   При этом принцип № 4 из `SPEC.md` (§ 1) прямо заявляет отказ от
   регулярного разбора Lua-вырезок — а `_expand` и `LuaDecl`-скан
   `re.finditer(r"\bfunction\s+(\w+)")` (`checker.py`) делают ровно это.

3. **`pass`/`stop` — один булев протокол с двумя разными следствиями.**
   Само отображение элементарно и не меняется: `pass` → `return false`,
   `stop` → `return` (`_handler_pair` для обработчиков, `_stmt` для блоков-значений),
   а движок читает результат как `r == false` → «не обработано»
   (`mp:runorval`, `data/stead3/parser/mp.lua:2233`) и всё остальное → «обработано».
   Проверено на текущем движке (см. § 6, п. 6):

   - в `before_Take` «не обработано» значит «выполни стандартную логику глагола»;
   - в `description`-блоке то же самое значит «после моего текста движок
     допишет свою строку» — для обычного предмета
     «Ты не видишь в ящике ничего необычного», для `openable`/`switchable` —
     состояние («Открыто»/«Выключено»);
   - `stop` в `description` глушит эту дописку, но одновременно глушит и всю
     последующую ветку `after_Exam` (содержимое контейнера, `Exam.SELF`, …).

   То есть семантика ключевого слова одинакова, а вот **следствие зависит от
   поля, в котором стоит блок**, и от того, что именно делает ветка
   «continue» в этом поле. Это по-прежнему нарушение «наименьшего удивления»:
   `pass` в описании выглядит как «мне нечего добавить», а получается
   «допиши за меня стандартную фразу». Именно поэтому `AGENTS.md` заводит
   отдельный пункт-предупреждение — документировать лекарство вместо того,
   чтобы сделать ошибку невозможной (например, разными типами блоков: `dsc`,
   где `pass` нельзя, и `before_*`, где он обязателен по смыслу).

4. **Печать внутри блока-значения — это не вывод, а построение значения.**
   `std.method` (`data/stead3/stead.lua:2632-2645`): если функция вернула
   `false` или `nil`, её возвращаемое значение **подменяется накопленным
   текстом** (`a, b = std.pget(), a`). Поэтому `say "…"` внутри `description`
   не печатает сразу, а складывает строку, которую движок затем напечатает
   сам (отсюда и то, что «дописать» текст в одном `say` или в двух — одно и то
   же). В MISE 2 обе роли — вывод сейчас и построение значения — записываются
   одинаково, одним и тем же оператором-строкой. Для автора это невидимая
   связка «эффект == значение», а для любого анализа это значит, что
   буфер печати — часть состояния мира, а не побочный вывод.

5. **Первая инструкция ветки диалога — не то же, что вторая.**
   `parser.py:703`: первый `p`-оператор тела `*`-выборки поднимается в
   `reply`, остальные — в `do`; эмиттер (`emitter.py:363+`) собирает из них
   один `act`, но при отсутствии `do` `reply` попадает в другую позицию
   таблицы `phr`. Значит, дописывание второй строки в ветку меняет структуру
   вывода. Автор не должен знать про `dsc`/`act`/позицию в таблице — это
   внутренность движка, просочившаяся в правила разбора.

6. **Дефолтные имена и «магии»:** `s`, `w`, `wh`, `w2`, `w3` как позиционные
   имена аргументов (`_handler_params`), зашитые цели `game`/`pl`/`mp`
   в двух слоях (`checker.py:775`, `emitter.py`), `__имя` как «динамическое
   поле», `#tag` как «разрешённый дубликат имени», `nam` как единственное
   read-only поле (`READONLY_FIELDS`). Каждое из этих правил — не модель, а
   частный случай.

7. **`f a b` без скобок с исключениями.** Идея ML-аппликации заявлена как
   единое правило, но она ограничена списком `STMT_KWS` (`parser.py:10`) и
   правилами `_can_start_arg` (`parser.py:908`), `not`-приоритетом «как в
   Python» и особым приоритетом `in`. Итог: `ids()` — ошибка («empty
   parentheses are not a call»), `say "{x}"` — печать, а `say f a b` — вызов
   `say` с тремя аргументами, `f a - 1` неоднозначно по пробелам (лексер
   решает по `spaced`). Это работает, но это **не одно правило**, а набор
   договорённостей; для автора они невидимы, пока он не наткнётся.

### 2.4. Строковые подъязыки внутри языка (главный дефект дизайна)

Язык тщательно проверяет типы значений — и **не проверяет вообще ничего** в том
месте, где живёт сама предметная область: паттерны глаголов и слова объектов.

- `patterns = ["~ {noun}/вн,scene в {noun}/пр,2,scene : Reflect reverse"]`
  — это мини-язык с метасимволами `~`, `*`, `~*`, `{noun}`, `{noun_obj}`,
  `{compass*}`, `/вн`, `/дт`, `,scene`, `,held`, `,supporter`, `,2`, `reverse`,
  `?в`, `:`. Практически ничего из этого не проверяется: единственное
  «понимание» — эвристика `_verb_pat_sig` (`checker.py:252`), которая делает
  `rsplit(":", 1)`, `.split()`, регуляркой ищет `{noun|noun_obj|compass*}` и
  **игнорирует** `,scene`/`,held`/падежи. Сигнатуры событий выводятся из этой
  эвристики; `,scene`-скоуп не моделируется вовсе.
- Паттерн без `:` молча не даёт сигнатуры (`return None`), а потом ошибка
  всплывает в другом месте — «unknown event» у обработчика.
- Слова объектов: `obj hook "крючок/мр,од|вешалка"` — падежи и граммемы внутри
  строки; опечатка в граммеме не диагностируется транспилятором (движок в
  рантайме пишет в stderr `Gram not found. Skip lex: …` — это видно при
  генерации `dict.mrd`).
- `{$fmt b|…}` — ещё одна строковая мини-разметка, разбираемая движком.

То есть **самая важная часть DSL (как игра реагирует на команды игрока) —
opaque-строка**. Всё остальное вокруг типизировано. Это прямо противоречит
цели «ошибки автора должны ловиться на сборке»: типичный баг автора IF —
опечатка в скоупе/падеже/имени события паттерна — проходит насквозь.

Отсюда же следует, что `_verb_pat_sig` — не анализ, а угадывание: она
приписывает слотам тип `obj`/`str` и угадывает `acted` по первому слоту.
Любая верификация выше типов начнёт с того, что паттерны надо распарсить
по-настоящему.

### 2.5. Мелкие расхождения спеки и реализации (симптом, не причина)

- ~~`SPEC.md` (§ 5, `base_type`) объявляет `list` базовым типом~~ — найдено
  и исправлено: `list` убран из `base_type` (он попадает туда как класс через
  `IDENT`), а в § 3.5 появился раздел про `tbl`/`tbl[T]`/`list`; сам дефект был
  именно в спецификации: `list` — класс движка (`class list = std.list`), и
  `fn ids() -> list` + `return []` законно даёт `expected list, got tbl[]`.
  Показательно, что расхождение прожило долго: `tbl`/`tbl[...]` вообще не были
  описаны в разделе про типы, и никто этого не заметил.
- `STRING` в EBNF поддерживает `"""…"""`, лексер — ещё и `'''…'''`.
- Описание «парсер контекстно-независимый» (§ 2) соседствует со значимыми
  отступами, которые лексер разворачивает в `INDENT`/`DEDENT` (это допустимо,
  но требует оговорки).
- `SPEC.md` § 5 описывает `fn_decl ::= "fn" IDENT … ( "=" raw_lua | stmt_block )`,
  а реализация принимает после `=` **один токен** (`parser.py`, `_parse_fn`:
  `self.eat(self.cur().kind).val`), поэтому `= x + 1` — ошибка парсера.
- В тестовом харнессе `tests/mise-check.py:59` — `"".join(difflib.unified_diff(...)[:40])`;
  `unified_diff` возвращает генератор, срез вызывает `TypeError`. Баг
  срабатывает **только при провале golden-теста**, то есть ровно тогда, когда
  нужен diff (наблюдал лично при рефакторинге).

### 2.6. Утечка плана реализации наружу

Вирт называет это «exposing your implementation plan». В MISE 2:

- **Порядок объявлений значим** (`_check_class_order`, `SPEC.md` § 3.6): класс
  должен быть объявлен выше использования. Это требование *эмиттера* (он
  сохраняет порядок операторов), а не языка; автор обязан думать как линкер.
  Текстовый `include` (склейка `prog.items`) усиливает эффект.
- **Существование функции в выводе зависит от её использования** (`_emit_fn`
  отбрасывает неиспользованные однострочные функции; `used_refs` включает и
  выключает эмиссию).
- **`std.fn_aliases` и строковые ключи `"before_Open,Close"`** генерируются
  конкатенацией в эмиттере; диспетчеризация живёт в `data/stead3` (Lua), а не
  в DSL.
- **`MATCH_TMP = "__match"`** и IIFE `(function(c) return … end)(subj)` для
  `in`-оператора — синтаксические трюки, видимые в сгенерированном Lua и
  влияющие на профиль (лишний closure на каждый `in` с непростым субъектом).
- **Нет карты строк**: ошибка рантайма указывает в `main3.lua`, а не в
  `game.mise`. Для языка, который позиционируется как author-facing, это
  дорогое отсутствие (лечится комментариями-маркерами при эмиссии).

### 2.7. Детерминизм

`_infer_sym` (`checker.py:1367`) при неоднозначности «значение принадлежит
нескольким перечислениям» делает `next(iter(owners))` — порядок зависит от
хеша строк. Для диагностики это значит: сообщение (и, теоретически, вердикт)
может отличаться между запусками. Дисциплина тут простая: неоднозначность —
это ошибка языка («`light` объявлен и в `attr`, и в `state`»), а не выбор
первого попавшегося.

## 3. Адекватность предметной области

### 3.1. Что на самом деле является доменом

Домен — не «синтаксис Lua для STEAD3». Домен — это: **мир (объекты, комнаты,
связи, замки, контейнеры, средства передвижения), правила реакции на действия
игрока, и прогресс (достижимость, разрешимость, отсутствие тупиков)**.

Лёгкие rule-driven системы (Wander-подобные) выигрывают именно потому, что
мир и правила записываются **в одной и той же форме** («шаблон → действие»),
и потому, что эта форма достаточно проста, чтобы её читать глазами и
анализировать программно. Inform 6/7 идут другим путём: библиотека задаёт
action-model, автор пишет правила, библиотека гарантирует единообразие
(и за счёт этого возможен `RULES`/`ACTIONS`-трассировка). Ink/Twine вообще
уходят в поток повествования. TADS 3 — это полноценный статически
типизированный ОО-язык с моделью мира в библиотеке. Dialog — Prolog-подобный,
и именно поэтому там возможен поиск/анализ.

### 3.2. Чем MISE 2 является на этом фоне

MISE 2 — это **сахар + тип-чекер для программиста STEAD3**, а не язык модели
мира. Это честная и полезная ниша (автор не переписывает `mp-ru.lua`), но она
означает:

- **Мир остаётся императивным.** Правила — это Lua-функции с побочными
  эффектами (`move`, `attr`, `enable`, `walk`, `take…`), а `before/after/post/life`
  диспетчеризуется движком по строковым именам. В DSL нет ни явного состояния,
  ни явных переходов, ни инвариантов.
- **Логика выбора команды непрозрачна.** Реальная семантика («какой глагол
  сматчится на этот ввод, что видимо в этой комнате, что в скоупе») живёт в
  `data/stead3/parser/mp.lua` (сотни строк) и вморожена в движок. DSL не
  описывает и не проверяет `scope`, `found_in`, `visible_scope` — только
  типы значений.
- **Абстракция течёт в самых частых местах.** Список «подводных камней»
  в `AGENTS.md` («Game DSL gotchas») — 8 пунктов про `scenery`, `container,open`,
  `pass` в `description`, `before_LetGo`/`after_LetIn`, атрибуты vs поля,
  `-"…"` — это и есть метрика протечки: если абстракция хороша, автору не
  нужно держать это в голове.
- **Диалоги** — самая удачная часть языка (`talk` в духе Ink), но и там
  маппинг на `phr`/`dsc`/`act`/`cond`/`next` приходится знать (§ 2.3, п. 5).

**Вывод по домену:** язык на 80 % решает *эргономику записи* и почти не решает
*структуру предметной области*. Для «автора текстовых игр» этого мало: автор
как раз слаб в императивной диспетчеризации и силён в «опиши мир и правила».
MISE 2 требует от него первого и лишь частично даёт второе. Это не приговор —
просто надо называть это правильно: не «DSL для писателей», а «безопасный
синтаксис для опытного автора STEAD3».

### 3.3. Масштаб относительно заявки

Заявка — компактный язык для писателей. Факт: 941 строка спецификации,
1000 строк парсера, 1600 строк чекера, 570 строк эмиттера, 248 строк
`core.mise`, ~50 отдельных диагностик. Компактные DSL живут, когда язык
помещается в голову (страница грамматики + страница правил). Здесь грамматика
~250 строк EBNF, а правил допустимости — ещё ~50 неформализованных. Это уже
не «маленький язык», это **средний компилятор с DSL-фасадом**. Само по себе не
плохо, но цена поддержки будет расти вместе с диагностиками, а не с языком.

## 4. Анализируемость и верификация

Ключевой вопрос: что можно доказать о программе на MISE 2 — сейчас и при
каких минимальных изменениях языка.

### 4.1. Что мешает уже на уровне модели

1. **Состояние не описано.** Нигде нет схемы состояния: множество объектов
   и полей задаётся декларациями, но их *значения* меняются произвольным
   Lua-кодом (`rawset` доступен, `setmetatable` доступен, `extern global`
   открывает `mp`, `std`, `game`, `pl`, `instead`, `snd`, `io`, `os`).
   Любой анализ обязан предполагать havoc.
2. **Переходы неявны.** «Команда игрока → изменение мира» реализуется в
   `mp.lua` (мэтчинг, скоуп) + `mplib.lua` (стандартные глаголы) + игра.
   DSL не содержит ни списка переходов, ни их предусловий/постусловий.
3. **Диспетчеризация по строкам и порядку.** `before_*`/`after_*`/`life_*`
   вызываются движком; результат «обработано/нет» — `false` vs `nil`/`true`,
   что проверяется только рантаймом.
4. **Недетерминизм и время:** `rnd`, `time()`, `once`, `daemon`-циклы,
   `each_turn`.
5. **Паттерны и слова — строки** (§ 2.4): даже «какие команды понимает игра»
   статически неизвестно; это надо вычислять по тексту паттернов эвристикой.
6. **API движка скопирован руками.** `core.mise` перечисляет события, их
   арности и шаблоны `extern`; ничто не проверяет, что это соответствует
   `data/stead3` (нет теста «объявленный extern существует в движке» и «все
   события движка объявлены»). Любая формальная модель мира, построенная поверх
   `core.mise`, будет тихо рассинхронизироваться с движком.

### 4.2. Что реально возможно (по возрастанию цены)

**(A) Fuzzing — да, дешево и полезно уже сейчас.**
Идея: автогенерация скриптов (существующий autoscript-формат!) из
алфавита = глаголы × объекты × направления, с фиксированным seed; инварианты
проверяются на выходе:
- нет Lua error / «no handler» / `attempt to index`;
- нет зависаний (есть `-stop`, есть timeout в харнессе);
- мир не «теряет» игрока (`where(me())` — всегда комната);
- достижимость: `ending`/`gameover` достигается (для коротких игр).
Это ловит краши и часть мёртвых состояний, но **не** доказывает отсутствие
тупиков. Цена: 1–2 дня, польза высокая, язык менять не надо.

**(B) Доменный линтер по декларациям — да, и это лучший ROI.**
Декларативная часть (`n_to`/`u_to`/`in_to`, `door_to`, `with_key`,
`found_in`, `with`, `attr`, `obj`-дети) уже образует граф мира. По нему
статически считаются классические IF-патологии:
- недостижимые комнаты и объекты (нет пути от стартовой комнаты);
- односторонние проходы (симметрия `n_to`/`s_to` там, где ожидается);
- ключ заперт за замком, который он же открывает (`with_key` внутри
  `locked`-двери/контейнера);
- `enterable`-транспорт без пути назад;
- комната без выхода вообще;
- объект, который никто и ничто не упоминает.
Всё это — без семантики Lua, только по AST деклараций + эвристике «есть ли
`before Open/Unlock`». Цена: 2–4 дня, польза огромная, полностью
детерминировано. Требует **канала предупреждений** (сейчас все диагностики —
жёсткие ошибки), это первое, что стоит добавить в архитектуру.

**(C) Abstract interpretation по «конечной абстракции мира» — возможно, но
только для подмножества.**
Реалистичная абстракция: атрибуты объектов — булевы (конечная решётка),
местоположение — `{комната, внутри контейнера, в руках, нигде}` (плюс имя
комнаты), счётчик — интервал, флаги — булевы. Тогда `move`, `attr`, `enable`,
`disable`, `take`, `drop`, `walk` интерпретируются точно, а произвольные тела
функций — как «havoc» (разрушение точности). Это даёт *предупреждения*
(«в этой ветке дверь может остаться запертой, а ключ внутри»), а не
доказательства. Чтобы это не тонуло в havoc, языку нужны аннотации
эффектов: `fn f(s: obj) -> bool @reads(open) @pure` и белый список
«интерпретируемых» builtin-ов. Сейчас такого понятия нет вообще (в DSL нет
даже `pure`, хотя в самом языке он был бы уместен: `extern value` уже
подразумевает «без побочных эффектов», но это нигде не проверяется).

**(D) Model checking — не сейчас.**
Требуется: (1) конечная схема состояния (см. C), (2) явная модель
диспетчеризации (какие обработчики могут сработать на какое действие),
(3) детерминизм (запрет/сидирование `rnd`/`time`), (4) генерация модели мира
из `core.mise`+деклараций. Первый шаг из этого списка — не «написать
model checker», а **дать языку state schema и effect annotations**. Без них
любая модель — это модель движка, а не игры; а моделировать весь STEAD3
(с его скоупами, падежами, `mp:noun_forms`, диалогами) — это отдельный
исследовательский проект, несовместимый с размером DSL.

### 4.3. Минимальные изменения языка, которые открывают анализ

Если ставить цель «верифицируемость» (а не только «удобство записи»), то
приоритет такой — и почти всё это обратно совместимо:

1. **Структурные паттерны вместо строк** (или хотя бы их полноценный разбор
   в чекере: `~`, `*`, `/падеж`, `,скоуп`, `reverse`). Это превращает «какие
   команды понимает объект» в статически извлекаемое множество — фундамент для
   (B), (C) и для диагностики `scope`.
2. **Канал предупреждений** (`warn(msg, line)`) + линтер мира (B).
3. **Эффект-аннотации/`pure`** и запрет havoc-builtin-ов в «проверяемых»
   играх (opt-in), что даёт (C).
4. **Явная схема состояния** (`state`/`world`-блок с типами и начальными
   значениями) — шаг к (D) и заодно к сериализации сейвов.
5. **Детерминизм**: `rnd`/`time` помечаются как эффекты; неоднозначные
   перечисления — ошибка.
6. **Генерация `core.mise` из `data/stead3`** (или тест соответствия):
   единый источник истины для событий/полей/`extern`-шаблонов.
7. **Гигиеничная подстановка** вместо `re.sub` (§ 2.3): параметры — через
   промежуточные `local`, шаблоны `$n` — только как позиции, а не текст.

## 5. Итоговая оценка

**Сильные стороны:** внятная модель значений (строки vs символы), один блочный
синтаксис, реальные статические проверки домена, отличная тестовая дисциплина,
аккуратная диагностика.

**Главный дефект дизайна:** язык описывает *синтаксис движка*, а не
*предметную область*. Самая доменная часть (паттерны, слова, скоупы,
диспетчеризация событий) осталась строковой и находится вне проверок, а
императивное состояние мира осталось снаружи модели. Из этого следуют все
остальные претензии: утечка порядка объявлений, макросы вместо функций,
`pass`/`stop` с контекстным смыслом, невозможность анализа выше типов.

**Оценка по осям:**

| Ось | Оценка | Комментарий |
|---|---|---|
| Дисциплина языка (Хоар/Вирт) | 6/10 | EBNF есть, но правила = 56 диагностик в коде; ортогональность и «наименьшее удивление» нарушены в 5–6 местах (§ 2.3) |
| Адекватность домену | 5/10 | Отличный слой текста/диалогов; но мир и правила остались императивными, а паттерны — строками |
| Компактность | 5/10 | ~3.7k строк компилятора + 941 строка спеки для DSL «для писателей» |
| Инженерное качество | 8/10 | Тесты, golden, транскрипты, `-stop`, сообщения; минус — баг в самом харнессе и регекс-макросы |
| Анализируемость | 4/10 | Fuzzing и линтер мира возможны и дешевы; model checking/abstract interpretation требуют изменений языка |
| Верифицируемость | 3/10 | Нет state schema, нет эффектов, нет детерминизма, нет модели диспетчеризации |

**Рекомендация:** не расширять язык новыми конструкциями. Сделать три вещи:
(B) линтер мира по декларациям + канал предупреждений, (A) fuzz-харнесс на
существующем autoscript-формате, и гигиеничную подстановку вместо `re.sub`.
Это даёт максимум пользы за минимум изменений. Разбор паттернов (1) и
эффект-аннотации (3) — следующий шаг, только если действительно нужна
верификация, а не проверка «на глаз».

## 6. Что проверено экспериментами

Всё это воспроизводимо на текущем `mise.py`:

1. `fn one_line(x: num) -> num = x` → `local a = (1)`; многострочный вариант →
   `fn_multi_line(1)`. Однострочность меняет макро/функцию.
2. `fn pick(o: tbl) -> any = \`(rawget(o, 1) or rawget(o, 2))\`` + вызов
   `pick mk` → `rawget(fn_mk(), 1) or rawget(fn_mk(), 2)`: аргумент вычислен
   дважды.
3. `fn ids() -> list` + `return []` → `return value 1 of ids: expected list,
   got tbl[]`: `list` — класс (`std.list`), а не встроенный тип; литерал `[...]`
   имеет тип `tbl[…]`. Была ошибка в `SPEC.md` (объявляла `list` базовым типом) —
   исправлена вместе с добавлением раздела про `tbl`/`tbl[T]`/`list`.
4. `say "{f '}'}"` и `say "{f(tostring(len({1, 2})))}"` до правки
   `_interp_end` разбирались неверно (`expected }, got '\n'`); после — корректно
   (коммит `566cf7e`, тест `tests/mise-interp`).
5. `tests/mise-check.py:59` падает с `TypeError: 'generator' object is not
   subscriptable`, как только golden-файл расходится.
6. `pass` vs `stop` в `description` — **проверено прогоном в движке** (не только
   кодом эмиттера), текущая сборка `reinstead`, два предмета в одной комнате
   с одинаковым текстом и разным завершителем:

   ```
   impl first        impl second
     found_in = hall   found_in = hall
     description =     description =
       say "Описание…"   say "Описание…"
       pass              stop
   ```

   Транскрипт: `осмотреть ящик` → «Описание первого. Ты не видишь в ящике
   ничего необычного.»; `осмотреть стол` → «Описание второго.» — без
   дописки. То есть `AGENTS.md` не устарел: протокол тот же
   (`data/stead3/parser/mp.lua:2233`: `if r == false then v = false`), но
   следствие зависит от поля.
7. Та же проверка подтверждает механизм `pget`
   (`data/stead3/stead.lua:2637`): текст, напечатанный внутри `description`,
   становится её возвращаемым значением (движок сам его выводит), поэтому
   `say` в блоке-значении — это построение строки, а не прямой вывод.
8. Сгенерированный Lua при генерации словаря печатает в stderr
   `Gram not found. Skip lex: …` — опечатка в граммеме слова не доходит до
   транспилятора (в том же тесте `obj first "первый"` не сматчился
   вообще: слова-прилагательные без граммем выпадают из словаря).
